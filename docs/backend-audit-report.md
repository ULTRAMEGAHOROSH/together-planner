# Together Planner — отчёт об аудите backend-спецификации

Объект аудита: `docs/backend-spec.md` (v1, 2026-11-12).
Результат: `docs/backend-spec-v2.md` и `docs/backend-implementation-roadmap.md`.
Дата: 2026-11-13.

---

## 1. Итог

Архитектура v1 в целом здоровая: модульный монолит, вычисляемая неделя, локальное время плюс пояс пространства, метка происхождения событий из шаблона, единый формат ошибок. Переписывать её не нужно.

Но найдено **4 критические проблемы** и **9 существенных**. В основном они касаются применения шаблонов, refresh-токенов и конкурентного доступа. Две критические гарантированно ломают функциональность при обычном использовании, без всяких гонок:
- **A-01:** перенос события из шаблона блокирует повторное применение этого шаблона;
- **A-02:** режим `REPLACE` падает на уникальном индексе из-за порядка flush в Hibernate.

| Критичность | Количество | Смысл |
|---|---|---|
| Critical | 4 | Ломает функциональность или теряет данные в обычном сценарии |
| High | 9 | Ошибка в реалистичном сценарии (гонка, второй таб, длинный пароль) или противоречие требованиям |
| Medium | 9 | Неточность, которая приведёт к багу или лишней работе при реализации |
| Low | 8 | Гигиена, документация, защита в глубину |

## 2. Найденные проблемы

Формат каждой записи: **где** → **суть** → **сценарий** → **критичность** → **исправление** → **что меняется в v2**.

### Critical

#### A-01. Защита от дублей ищет уже созданные события только среди событий недели
- **Где:** v1 §7.5, шаг `existing = события, пересекающие неделю`; проверка `a)` ищет дубль в `remaining`.
- **Суть:** признак «уже применено» — пара `(source_template_event_id, source_week_start)`. Но кандидаты загружаются по времени (пересечение с неделей), а не по этому признаку. Событие, которое пользователь перенёс за пределы недели, в выборку не попадает.
- **Сценарий:**
  1. «Обычная неделя» применена к 09.11.
  2. Пользователь переносит «Работу» с пн 09.11 на пн 16.11.
  3. Повторный MERGE к 09.11: планировщик не видит перенесённое событие и планирует создать его снова.
  4. Уникальный индекс `uq_event_template_source` отвергает вставку, вся транзакция откатывается.
  5. **Любое** следующее применение шаблона к этой неделе навсегда падает с `409`.
- **Критичность:** Critical.
- **Исправление:** дубли ищутся **отдельным запросом** по признаку: `source_week_start = :week AND source_template_event_id IN (:templateEventIds)`. Выборка по времени нужна только для конфликтов, FILL и REPLACE.
- **В v2:** §9.3 (входные данные планировщика), §9.4 (алгоритм), §6.4 (`EventService.findBySourceWeek`), §14.2 (кейсы M3, R4).

#### A-02. REPLACE нарушает уникальный индекс из-за порядка flush в Hibernate
- **Где:** v1 §7.5, `apply`: сначала удалить, затем создать.
- **Суть:** Hibernate выполняет SQL при flush не в порядке вызовов, а по типам действий: **INSERT раньше DELETE**. При REPLACE удаляется событие `(t1, W)` и создаётся новое с тем же `(t1, W)`. INSERT уходит первым и нарушает `uq_event_template_source`.
- **Сценарий:** любой REPLACE недели, к которой этот шаблон уже применялся (а это основной сценарий REPLACE), падает с `409 TEMPLATE_APPLY_CONFLICT`.
- **Критичность:** Critical.
- **Исправление:** `EventService.deleteForTemplateReplace(...)` удаляет события и **сразу вызывает `flush()`**. Только после этого создаются новые. Это обязательный шаг алгоритма, и его проверяет интеграционный тест.
- **В v2:** §9.5 (шаг 7), §6.4, §14.3 (тест I-12).

#### A-03. REPLACE может удалить событие, которого пользователь не видел в предпросмотре
- **Где:** v1 §5.7: «T7 планирует заново… применится актуальный план».
- **Суть:** перестроить план внутри транзакции правильно, но для удалений это опасно. Между предпросмотром и подтверждением партнёр может создать событие. При `includeManual = true` оно будет удалено без показа.
- **Сценарий:**
  1. Daulet открывает предпросмотр REPLACE с `includeManual` и видит «−5».
  2. В это время партнёр создаёт «Врач» на этой неделе.
  3. Daulet подтверждает — «Врач» удалён, хотя в предпросмотре его не было.
- **Критичность:** Critical (молчаливая потеря данных).
- **Исправление:** для REPLACE запрос apply обязан содержать `confirmedDeleteIds` — id событий, показанных в предпросмотре. Если реальный набор на удаление отличается → `409 APPLY_PLAN_OUTDATED`, ничего не меняется, frontend заново запрашивает предпросмотр. Добавления так не подтверждаются: они не разрушают данные и видны в результате.
- **В v2:** §8.8 (DTO, T7), §9.5 (шаг 6), §7.4 (код ошибки), §14.3 (I-13).

#### A-04. Удалённое пользователем событие из шаблона восстанавливается при повторном применении
- **Где:** v1 §5.5, E6: «повторный MERGE создаст его снова — это ожидаемо».
- **Суть:** это противоречит требованию «применение шаблона не должно случайно…» и прямому требованию аудита не допускать восстановления удалённого. Пользователь удалил «Тренировку» в среду, затем повторно применил шаблон ради новых событий — «Тренировка» вернулась.
- **Критичность:** Critical (нарушение бизнес-требования).
- **Исправление:** таблица исключений `template_occurrence_exclusion (template_event_id, week_start)`:
  - Когда пользователь удаляет событие, у которого есть происхождение, в той же транзакции создаётся исключение.
  - MERGE и FILL пропускают исключённые вхождения и показывают их как `skippedDeleted`.
  - REPLACE означает «применить заново целиком». Он восстанавливает такие вхождения, явно показывает их в предпросмотре как `restoredDeleted` и удаляет исключения.

  Связь между модулями: модуль `event` публикует прикладное событие Spring `TemplateOccurrenceDeletedEvent`. Модуль `template` слушает его синхронным `@EventListener` в той же транзакции. Модуль `event` при этом ничего не знает о шаблонах.

  Почему не мягкое удаление (`deleted_at`): тогда каждый запрос к событиям должен помнить про фильтр, и одна забытая проверка покажет удалённое событие.
- **В v2:** §4.2 (таблица), §5.4 (V4), §6.3 (связь модулей), §9.2, §9.4, §14.2 (M4, R3), §14.3 (I-11).

### High

#### A-05. Конкурентные refresh-запросы: двойная ротация и ложное обнаружение кражи
- **Где:** v1 §7.4.
- **Суть:** у алгоритма «прочитать → проверить `revokedAt` → отозвать → выдать новый» две проблемы.
  - **Гонка в БД.** Два запроса читают токен одновременно, оба видят его активным, оба выдают новые. В итоге два живых потомка, и ротация обойдена.
  - **Ложная тревога.** Два таба (или повтор запроса после обрыва сети) отправляют одну и ту же cookie. Первый ротирует, второй через миллисекунды видит отозванный токен → «кража» → отозваны **все** сессии пользователя. При нормальной работе SPA это случается регулярно.
  - **Откат отзыва.** Массовый отзыв выполнялся перед `throw` внутри `@Transactional`. `RuntimeException` откатывает транзакцию, и отзыв не сохраняется.
- **Критичность:** High.
- **Исправление:**
  1. Отзыв — атомарный условный UPDATE: `… SET revoked_at = :now, revoke_reason = 'ROTATED' WHERE id = :id AND revoked_at IS NULL`. Если обновлено 0 строк, гонку выиграл другой запрос.
  2. Окно 10 секунд: токен, отозванный ротацией не больше 10 секунд назад, даёт `401 REFRESH_TOKEN_ROTATED` без побочных эффектов. Frontend делает один повтор: браузер к этому моменту уже получил новую cookie.
  3. Массовый отзыв (`REUSE_DETECTED`) — только для ротированного токена старше окна.
  4. Метод помечен `@Transactional(noRollbackFor = ApiException.class)`, чтобы массовый отзыв сохранился, несмотря на ответ 401.
  5. Добавлена колонка `revoke_reason`, иначе нельзя отличить ротацию от logout.
- **В v2:** §4.2, §5.1 (V1), §10.4, §14.2 (RT1–RT6), §14.4 (C-03), §14.5 (S-09).

#### A-06. FILL игнорирует многодневные события
- **Где:** v1 §7.5: день занят, если есть событие, *начинающееся* в этот день.
- **Суть:** поездка пт 08:00 – вс 20:00 начинается в пятницу. Суббота и воскресенье считаются свободными, и FILL добавляет туда «Работу».
- **Критичность:** High (нарушение смысла режима: «только в свободные дни»).
- **Исправление (решение Q-1):** день D занят для участника, если у него есть событие, **пересекающее** `[D 12:00; D+1 00:00)`. Проверяется пересечение интервалов, а не дата начала, поэтому поездка занимает каждый день, на который заходит после полудня. Событие, которое заканчивается ровно в 12:00 или раньше, день не занимает. Порог — одна константа `BusyDayRule.BUSY_FROM`.
- **В v2:** §2.2 (D-4), §9.1, §9.4, §14.2 (BD1–BD10, F1–F10).

#### A-07. Конфликты ищутся только внутри недели
- **Где:** v1 §7.5: `existing` ограничен неделей.
- **Суть:** вхождения шаблона выходят за неделю. «Сон» вс 23:00 + 8 ч заканчивается в пн следующей недели, а длительность в шаблоне может доходить до 7 суток. Пересечения с событиями следующей недели не находятся.
- **Критичность:** High.
- **Исправление:** окно загрузки `[weekStart; weekStart + 14 дней)`: неделя плюс максимальная длительность события шаблона. Для REPLACE и FILL фильтры дополнительно сужаются до недели и дня.
- **В v2:** §9.3, §14.2 (M8).

#### A-08. Межмодульный API отдаёт JPA-сущность
- **Где:** v1 §7.5, `List<Event> findOverlapping(...)` как API модуля `event` для `template`.
- **Суть:** нарушает правило самой спецификации («не используй entity чужого модуля»). Модуль `template` получает управляемые сущности, может случайно их изменить или вызвать lazy-загрузку.
- **Критичность:** High (архитектурная граница).
- **Исправление:** через границу модулей передаётся публичный неизменяемый DTO модуля `event` — `EventResponse`. В нём уже есть id, время, участники и происхождение; отдельный тип-снимок не нужен. Полный список публичных методов каждого модуля — в §6.4.
- **В v2:** §6.4.

#### A-09. Пароль ограничен в символах, а BCrypt — в байтах
- **Где:** v1 §5.2, `@Size(max = 72)`.
- **Суть:** `@Size` считает символы. Кириллический символ занимает 2 байта в UTF-8, то есть 72 символа — до 144 байт. Начиная со Spring Security 6.3 (в том числе 7.1 из Boot 4.1.2) `BCryptPasswordEncoder` бросает `IllegalArgumentException` для паролей длиннее 72 байт.
- **Сценарий:** пароль из 40 кириллических символов → `500 INTERNAL_ERROR` при регистрации.
- **Критичность:** High.
- **Исправление:** `@Size(min = 8, max = 72)` оставить как грубую проверку, а в сервисе дополнительно проверять `password.getBytes(UTF_8).length <= 72` → `400 PASSWORD_TOO_LONG`.
- **В v2:** §8.3, §10.2, §7.4.

#### A-10. Нарушения ограничений БД превращаются в общий `DATA_CONFLICT`
- **Где:** v1 §6.2.
- **Суть:** проверка «email свободен» и INSERT разделены во времени. Две одновременные регистрации с одним email: проверку проходят обе, вторая падает на `uq_app_user_email` и получает `409 DATA_CONFLICT` вместо `EMAIL_ALREADY_REGISTERED`. То же для имени шаблона, места в пространстве и дублей шаблона.
- **Критичность:** High (непредсказуемый контракт API в гонках).
- **Исправление:** `ConstraintErrorMapper` — таблица «имя ограничения → `ErrorCode`». Имя берётся из `org.hibernate.exception.ConstraintViolationException#getConstraintName()`. Проверки в сервисах остаются как быстрый путь и для понятных сообщений, а БД — как последний рубеж.
- **В v2:** §7.3.

#### A-11. Лимит в 2 участника держится только на сервисе и пессимистической блокировке
- **Где:** v1 §3.2 (V2), §7.3.
- **Суть:** правило «максимум 2 участника» не закреплено в БД. Ради него join берёт `SELECT … FOR UPDATE` — это лишняя блокировка (против требования «не ставить pessimistic locking повсюду»).
- **Критичность:** High.
- **Исправление:** колонка `seat smallint CHECK (seat IN (1, 2))` + `UNIQUE (workspace_id, seat)`. Третьего участника БД физически не примет. Блокировка join больше не нужна: гонку разрешает уникальный индекс, а `ConstraintErrorMapper` превращает нарушение в `409 WORKSPACE_FULL`. Заодно `seat` задаёт стабильный порядок панелей: 1 — левая, 2 — правая.
- **В v2:** §4.2, §5.2 (V2), §9.6, §11.

#### A-12. Противоречивые варианты стека (Boot 3.5 / 4) и несуществующий генератор UUID
- **Где:** v1 §0, §3.1, §8, §10.
- **Суть:**
  - v1 советовал Boot 4 и параллельно описывал Boot 3.5 — два варианта реализации в одном документе.
  - `@UuidGenerator(style = VERSION_7)` **не существует в Hibernate 6.6.53** (в `UuidGenerator.Style` есть только `AUTO`, `RANDOM`, `TIME`; проверено по классу в jar). Код не скомпилируется.
- **Критичность:** High.
- **Исправление (решение Q-5):** стек зафиксирован — **Spring Boot 4.1.2** (Hibernate 7.4.13). В Hibernate 7.4 `Style.VERSION_7` есть, поэтому id — UUID v7 через `@UuidGenerator(style = VERSION_7)`. Описания Boot 3.5 удалены. Отдельно описана ловушка: если присвоить id вручную в конструкторе, Spring Data посчитает сущность не новой, и `save()` сделает лишний SELECT и `merge`.
- **В v2:** §1, §5.0, §12.1.

#### A-13. Модель CSRF и размещения не зафиксирована
- **Где:** v1 §7.4: `csrf.disable()` с одной строкой обоснования.
- **Суть:**
  - Не выбрана схема размещения. `SameSite=Strict` работает только когда frontend и backend на одном сайте. Если их разнести по разным доменам, cookie перестанет отправляться, refresh сломается, а «починка» через `SameSite=None` откроет CSRF.
  - Не разобрано, что `/auth/refresh` и `/auth/logout` — POST без тела, то есть «простые» CORS-запросы без предварительной проверки. Их может отправить чужой сайт.
- **Критичность:** High.
- **Исправление:**
  - Схема размещения — **один origin** (решение Q-4): nginx отдаёт SPA на `/` и проксирует `/api` на backend; в разработке то же делает proxy Angular. CORS не настраивается вовсе.
  - Явно записано, что один origin **сам по себе не защищает от CSRF**: чужой сайт всё равно может отправить запрос на наш origin. Разобраны все запросы с cookie, включая login CSRF.
  - CSRF-фильтр Spring отключён с полным обоснованием: защищённые API аутентифицируются заголовком `Authorization`, который браузер сам не подставляет.
  - Для cookie-эндпоинтов защита в глубину: обязательный заголовок `X-Requested-With`. Чужой origin не может отправить его без CORS-разрешения.
  - Раздельное размещение явно описано как вне рамок MVP, с перечнем того, что тогда придётся поменять.
- **В v2:** §10.5, §10.6.

## 3. Время и часовые пояса — вывод аудита

Модель v1 (**локальное время + один IANA-пояс на пространство**) признана правильной для MVP и сохранена. Обоснование и разбор:

| Аспект | Решение | Почему |
|---|---|---|
| Локальное время расписания | Источник правды: `timestamp` ↔ `LocalDateTime` | Планировщик оперирует местными часами: «Работа в 09:00». Смена правил пояса не сдвигает будущие события. Пример: переход Казахстана на UTC+5 в 2024 году |
| Абсолютный момент | **Не хранится**, вычисляется при необходимости: `ZonedDateTime.of(local, zone).toInstant()` | В MVP не нужен (нет уведомлений). Если хранить его, будет второй источник правды |
| Часовой пояс | `workspace.time_zone`, только region-id | Оба участника живут в одном поясе — допущение Этапа 0. Фиксированные смещения запрещены (A-18) |
| Переход DST | Несуществующее время сдвигается вперёд на длину разрыва; неоднозначное сохраняется как есть и при переводе в момент берёт раннее смещение. Длительности — по местным часам | `ZonedDateTime.of` делает это сам. В `Asia/Almaty` DST нет, но логика корректна для любого пояса |
| Через полночь | `end` на следующей дате; неделя — по пересечению интервалов | Обрезку и разрез по дням делает frontend |
| Поездки | Время вводится в поясе пространства; у события нет своего пояса (решение Q-6) | Осознанное ограничение MVP |
| Смена пояса пространства | События сохраняют местные дату и время; данные не мигрируются; «сейчас» считается в новом поясе | spec §3, правило 9 |

Технические поправки: A-18 (только region-id) и правило минутной точности.

## 4. Что оставлено без изменений

- Модульный монолит и набор модулей: `common`, `config`, `security`, `auth`, `user`, `workspace`, `event`, `schedule`, `template`.
- Направление зависимостей и правила «между модулями — по ID, только через сервис».
- Отсутствие таблицы `WeeklySchedule`: неделя вычисляется из событий.
- Происхождение события (`EventSource`: id события шаблона, неделя, снимок имени) и частичный уникальный индекс.
- `template_application` — журнал со снимком имени шаблона и `ON DELETE SET NULL`.
- `duration_minutes` вместо `end_time` в шаблоне.
- Единый поток предпросмотр → применение через один планировщик с перестроением плана в транзакции. Добавлено подтверждение удалений (A-03).
- Diff по id при обновлении шаблона.
- `ProblemDetail` + `ErrorCode` (enum со статусом) + единственное `ApiException`.
- DTO как `record`, участники как `@ElementCollection Set<UUID>`, `default_batch_fetch_size`.
- Оптимистическая блокировка с явным сравнением версии из DTO.
- `404` вместо `403` для чужих ресурсов, вложенные URL `/api/v1/workspaces/{wsId}/…`.
- Access-токен в памяти, refresh в cookie `HttpOnly` + `SameSite=Strict` с узким `Path`, хеш SHA-256.
- Цвет события как ключ палитры, а не hex.
- Ограничение длительности события в 31 день ради диапазонного поиска по индексу.
